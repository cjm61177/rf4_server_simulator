# 修复丢弃鱼竿后强退及背包加载异常

Status: done

## Problem Statement

玩家在背包主动丢弃初始鱼竿后出现强退或重新登录异常；本轮修复过程中又发现背包持续显示“正在下载”。仅删除物品行无法保证装配、持竿和持久化钓鱼状态均不再引用已删除的鱼竿，旧版本留下的错误物品类型也需要恢复。

## Solution

丢弃鱼竿后，仍存在的配件回到背包，失效的装配和持竿引用被清理，玩家能够重新登录并读取背包。历史异常存档在正常修复和登录流程中恢复，其他物品、余额及正常钓组保持有效。邮件组合包的发放和商店使用一致的数量规则，避免重新引入错误实例或数量。

## User Stories

1. 作为玩家，我希望丢弃初始鱼竿后仍能继续使用背包并重新登录，剩余配件能够保留。
2. 作为已有存档的玩家，我希望历史残留引用和错误物品类型能够恢复，不必重置角色或补发鱼竿。
3. 边界：重复删除、重复领取、事务失败、其他玩家物品及正常钓组均不能产生额外发放或部分更新；鱼护放生保持现有行为。

## Implementation Decisions

- `internal/gameserver` 的物品删除与玩家登录入口负责失效装配和持竿状态清理；在线状态只在数据库提交成功后更新。
- `internal/store` 的物品删除逻辑允许在已有事务中执行，保留玩家归属检查、重复 GUID 处理和鱼护放生语义。
- 物品删除、附件退包、装配索引和持久化钓鱼状态的更新保持同一事务；事务内只通过该事务访问数据库，定义准备在事务前完成。
- 背包历史错类恢复沿用已有 `RepairItemPhysics` 和类别 55 换类支持，增加真实旧行到背包完整读取的回归，不重复覆盖上游类型映射。
- 邮件组合包与商店复用展开逻辑，保留普通附件快照语义；事务失败不消耗附件，数量必须满足协议字段范围。
- 不增加命令或修改响应形状、表结构、静态库内容；客户端兼容基线为 `4.0.25034`。
- 所有数据修复须幂等；异常定义或不可保真的附件保留并返回失败，不通过删除玩家物品规避加载错误。

## Testing Decisions

- 存储层使用真实临时 SQLite、当前迁移和独立静态定义模板；测试数据准备失败必须使新增用例失败，不能跳过。
- 丢竿回归覆盖主动删除后重建服务器登录、历史残留修复两次、附件退包、装配与快捷栏引用、在线和持久化持竿状态，以及整体回滚、正常钓组和其他玩家隔离。
- 背包回归构造旧鱼线类型的组合包行，通过启动修复和登录后执行 `4/1`、`4/4`、`4/5` 编解码回环，检查数量、GUID 与详情一致，并检查余额和正常物品不变。
- 邮件组合包保留数量手算断言：两包 × 每包六瓶 × 每瓶两份 = 24 份；覆盖普通邮件、旧快照、独立工具实例、重复领取、无效定义和失败回滚。
- 移除丢竿清理后，对应删除、登录及回滚用例应变红；移除组合包领取修复后，邮件展开和数量用例应变红。旧物品类型恢复由已有上游修复承担，相应回归用于确保整条路径可用。
- 完成前运行受影响用例以及 `go test ./...`、`go vet ./...`、`go build ./...`，如有上游跳过或失败须明确说明。

## Out of Scope

不修改断竿或鱼获奖励机制，不补发新手鱼竿，不重置角色，不修改共享 BUG 文档，不部署或重启现有服务，不处理其他背包卡顿来源。

## Further Notes

- [事实] 用户反馈的顺序为丢竿后强退或重登异常，首次修复后发现背包打不开，补修后确认本地部署恢复；不能据此认定两种表现具有同一根因。
- [事实] 当前上游已包含类别 55 的正确实例映射及旧鱼线回退类的启动换类处理。
- [事实] 旧版异常组合包来自补偿邮件；其来源不代表本轮修复的全部范围。
- [未验证] 本次与最新上游适配后的完整版本尚未再次部署进行客户端验证，既有客户端确认仅适用于此前部署版本。
- [事实] 本次原生全量测试、静态检查和构建通过。临时启用上游数据库模板后的扩展全量仍有两条拟饵用例等待启动推送超时；干净基线已在同一位置复现，按既有失败在 PR 中披露。
