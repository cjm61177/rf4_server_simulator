# 稀有鱼 / 超级稀有鱼 鱼种数奖座

Status: in-progress

## Problem Statement

官方按「图鉴里有多少**种**稀有鱼」发奖座（`statuette_fisherman_<n>`「N条稀有鱼」、
`statuette_supertrophy_<n>`「N条超级稀有鱼」），本服此前完全没有这条链路：玩家把稀有鱼
图鉴刷到上百种，背包里一枚奖座都没有。

补回时还要解决一个口径问题：图鉴（3/17 面板、307.f16 等级旁星号）只认 `catch_log`，
而 `catch_log` 只在 14/5 **入护**时写入，14/6 放生的鱼不写。奖座如果按「钓到就算」发，
玩家会拿到「背包有奖座、图鉴不计数」的结果，长期看会怀疑进度算错。

## Solution

玩家把某个新鱼种**钓上来并入护**、使图鉴跨过一档（稀有鱼 3/5/10/…，超级稀有鱼 1/3/5/…）时，
奖座直接进背包，系统频道播报一行「收藏奖座解锁：<物品名>（稀有鱼图鉴 N 种）」。
放生的鱼不计数、也不发奖座——与图鉴、星号完全同一条准入线。

已经刷过头的老存档，登录后一次性补发所有跨过而未发的档位（可一次连发多枚）。

## User Stories

1. 作为玩家，我希望钓到并**收进鱼护**的第 3 种稀有鱼能立刻给我「3条稀有鱼」奖座，
   以便图鉴进度和收藏品对得上。
2. 作为玩家，我希望钓到新鱼种又放生时**不**给我奖座，因为图鉴也不记这条；
   这样我看到面板 87 种就有 87 种的对应奖座，不会出现「奖座比图鉴多」。
3. 作为老玩家，我希望登录后自动补齐历史进度（例如图鉴已 110 种时，75 与 100 两档
   一起到账），不必再钓一条鱼触发。
4. 边界：奖座卖掉/丢掉不重发（发放记录在 `kv`，不看背包）。
5. 边界：同一鱼种第二次上星不推进进度；蓝冠既算超级稀有鱼、也算稀有鱼。
6. 边界：护网已满导致入护失败时，什么都不发，玩家腾出位置重试后照常发。
7. 边界：重复入护（重放 14/5）不重复发；结算后断线，重连拉背包列表也能看到奖座。

## Implementation Decisions

- 计数：`internal/gameserver/rarity_milestones.go`，`catch_log` 上
  `COUNT(DISTINCT fish_key)`，稀有鱼 `grade>=3`、超级稀有鱼 `grade>=4`（蓝冠同时计入两族）。
- 判定时机：**14/5 入护落库之后**（`fishingKeep` 里 `keptInNet` 为真时），入口
  `rarityMilestoneAfterKeep`。14/4 结算与 14/6 放生都不判定，因此不存在
  「结算界面弹了奖座、随后放生」的窗口。
- 兜底：登录 3/1、打开 3/17 面板、背包列表 4/1 与 4/4（每会话一次）都调
  `ensureRarityMilestones`，覆盖「入护那一刻发放失败」和「补丁上线前的老存档」。
- 幂等：每档一枚 kv 标记 `rarity-milestone:<uid>:<rare|super>:<档位>`，与物品发放
  同一事务提交（`INSERT OR IGNORE` 抢标记，抢到才发）。**不复用**结算回执键：
  回执是按“这一次钓获”生成的（`catch-release:<uid>:<guid>`、结算 kv），一次结算只对应
  一尾鱼，而奖座是按“累计鱼种数”发放、一次可能连跨数档，两者生命周期不同；
  也不复用 `catch_log` 的唯一索引，因为同一鱼种可以有多条入护记录。
- 已发但标记丢失（手工改库/回滚）时按 `item` 表里是否已有该 `item_id` 判断，只补标记。
- 到账表现：`pushItemUpdate` 推 4/22 + `pushSystemChat` 播报。**不占** `801.f4`：
  入护走的是 800，没有结算礼物卡；`801.f4` 因此只剩升级礼物一种来源码。
- 不改表结构、不改协议字段、不改静态库。奖座物品本身已存在于 `item_def`。
- 回滚：删除 `rarity_milestones.go` 与 `fishingKeep` 里的调用即可；已发物品与 kv 标记
  保留在库里，回滚后不会触发任何已有逻辑。

## Testing Decisions

- 接缝：真实 SQLite（`newRigTestServer`）+ 行为链路，直接走 14/4 `fishingEndSettle`
  与 14/5 `fishingKeep` / 14/6 `fishingRelease`，不 mock 存储。
- 期望值来自官方物品名（「3条稀有鱼」= 3 种）与档位表字面量，不由被测代码反推。
- 覆盖：跨档入护发奖座、结算阶段不发、放生不发（且 catch_log 不落行）、放生后入护
  仍不发、同鱼种重复上星不推进、首冠只发超级稀有鱼那一族、登录巡检补发可跨多档且幂等、
  档位表与 `item_def` 逐档对齐。
- 回滚后变红的测试：`rarity_milestones_test.go` 全部（含新加的放生用例）。

## Out of Scope

- 不放宽图鉴口径（不放生的鱼仍然不计入 3/17 面板与 307.f16 星号）。
- 不新增奖座档位、不改物品表与本地化文本。
- 不做“奖座可交易/可回收”等经济玩法。

## Further Notes

- `[事实]` `catch_log` 只在 14/5 入护写入、放生不写：`econ.go` 注释与
  `achievements_rules.go` 的 `distinctCatchBaits` 同源说明，`releaseCatchOnce` 无
  `catch_log` 插入语句。
- `[事实]` 奖座名自带档位（`statuette_fisherman_3` = 「3条稀有鱼」），档位表由
  `TestRarityMilestoneLaddersMatchItemDefs` 对 `item_def` 逐档核对。
- `[事实]` `801.f4` 来源码 5「钓到了数条稀有鱼」在客户端本地化里存在
  （`kDlg_Catched_GiftsTrophyCountReached`），但本次不依赖它：奖座不经过 801。
- `[推断]` 系统频道播报文案复用 `pushSystemChat` 通道（福袋开箱、等级礼物已在用），
  真机表现与这些提示一致；未单独抓包验证。
- `[假设]` 官方同样是「入护才算图鉴」——依据是 3/17 面板与星号都只由 `catch_log` 驱动；
  若官方实际按“钓到即算”，只需把判定挪回 14/4，测试改回 801 断言即可。
