# 断件后果按四态分流

Status: done

## Problem Statement

搏鱼时力度条打满红色、客户端已经播了断件动画，服务端结算出的后果和官方实测对不上：
断主线只扣固定几米、断竿把完好配件摘回背包、断轮把整套钓组清空并判跑鱼。玩家看到的
是"断是断了，但代价和官方不一样"，承力选择的取舍也跟着失真。

终端件（钩、拟饵、饵、浮漂）断裂后被退回背包，等于断了不掉。

## Solution

断件后果按四态分流，断哪一环就丢哪一环，且只丢该丢的部分：

- **清杯断主线**：主线整条丢失并销毁，主线下方的引线、钩、饵一并消失，竿与轮不动；
  剪线（`17/10`）是另一条语义，只按上报米数扣减，不销毁整条线。
- **断竿**：竿梢折断——竿本体耐久归 0、竿上的渔轮保留，主线与挂线配件全部丢失；
  断竿时把销毁组件放进 `11028` 的移除列表，客户端只按这份列表清线组。
- **断轮**：轮子耐久归 0 留在竿上，钓组与已上钩的鱼全部保留，只是收不动线；
  搏鱼继续，等客户端断线或玩家剪线收尾；报废轮子不能再抛投。
- **终端件断裂**：钩、拟饵、饵、浮漂即丢失销毁，不退背包，不影响竿本体与承力线。

## User Stories

1. 作为玩家，我把线组拼到极限后，装备会按断在哪一环而损失对应部件，承力选择有真实代价。
2. 作为玩家，断轮后我还能把当前这条鱼搏完或剪线收尾，但不能再抛下一竿。
3. 作为玩家，断竿后我手里是断竿，轮子还挂在上面，换一根竿就能继续玩。
4. 边界：同一次断件上报重复到达（客户端重发 `17/9`）只结算一次，不会二次扣件。
5. 边界：断件与钓获结算并发时，以先落库的一方为准，另一侧看到的是已清理的钓组。
6. 边界：从背包堆拆出的子饵随终端件销毁时，来源堆数量在装配时已减，
   结算后要把来源堆 GUID 一并推 `4/22` 对齐，避免客户端数量与库内不一致。

## Implementation Decisions

- `internal/gameserver/gear_damage.go`
  - `gearBreakOutcome` 新增 `KeepFight`：渔轮损坏但钓组与鱼都保留时置真，调用方据此
    不按跑鱼收尾。`damageReelSlip`（摩擦片磨穿）同样置真——泄力失效不等于鱼脱钩。
  - `lineLossPolicy` 新增 `destroyLine`：`17/9` 断主线走销毁整条，`17/10` 剪线仍按米扣减。
    删除原 `lineBreakLoss` 的随机扣减兜底，缺长度参数一律按整条处理。
  - `breakComponentTx` 不再把终端件退回背包，改为随事务级联删除；子实例的来源堆在
    事务提交后再收集（单连接测试库在事务内另开连接会死锁），随结果一起推 `4/22`。
  - `damageReelLockOverload` 不再摘除钓组组件、不再清补饵请求与饵-钩映射——钓组原样
    保留，鱼仍咬钩，与官方「轮子报废但线组还在」一致。
  - `breakRodTx` 保留竿上的渔轮引用（f4），其余挂线配件改为级联删除并记
    `lost_on_rod_break` 伤害事件；被销毁的拆分子饵在事务提交后回查来源堆并推 `4/22`。
  - 新增伤害事件 `lost_on_rod_break`，后台可追溯因断竿而销毁的组件。
- `internal/gameserver/protocol_dynamic_handlers.go`：`hDynamicRodBreak` 按 `KeepFight`
  分流——为真时不清 `Pending`/`Hooked`/`Resolved`、不记跑鱼、不推跑鱼提示，
  只推「无法收线，鱼仍在钩上」；其余分支保持一次性收尾并计对应计数。
- 数据与迁移：不改表结构，无迁移。
- 兼容：客户端基线 `4.0.25034`；报文依据为 `17/9` 上报件类别、`11028` 移除列表与
  `4/22` 物品刷新；回滚方式为 revert 本提交，无数据残留。

## Testing Decisions

- 测哪一层：存储层用真实 SQLite（`newRigTestServer`），走真实断件结算入口，不打桩；
  协议层只校验响应中哪些 GUID 进入移除列表。
- 期望值来源：官方四态口径的字面描述——每个用例断言「哪些 GUID 还在、哪些必须消失」，
  以及被销毁组件的来源堆数量是否与装配时的扣减一致（`3 → 2` 而不是回补成 `3`）。
- 覆盖：`gear_break_official_rules_test.go`（四态主链路）、`gear_damage_test.go`
  （断竿清钓组、断轮保留钓组与补饵设置）、`gear_break_residue_test.go`（残留物）、
  `hook_break_test.go` 与 `break_report_fallback_test.go`（终端件与回退路径）、
  `reel_drag_break_test.go`（断轮后抛投拦截）。
- 回滚后这些用例会变红，可据此确认覆盖有效。

## Out of Scope

- 不改耐久折算公式与摩擦片过热口径。
- 不建模修竿、修轮的经济与耗时。
- 不处理"断件后背包与客户端显示不同步"的个别边界，这类问题另开改动。
- 不新增客户端协议字段。

## Further Notes

- `[事实]` 四态行为描述来自游戏内提示与官方修复指南，以及 `internal/gameserver`
  既有协议字段的实测来源（`17/9` 上报件类别、`11028` 移除列表、`4/22` 损坏位）。
- `[推断]` 断轮后「钓组原样保留、鱼仍咬钩」取自客户端在轮子报废后仍允许继续搏鱼的表现。
- `[未验证]` 满红炸线的实机回归尚未执行，验证方式是在纺车轮上把力度条打满，
  确认对应部件真的消失、后续抛投与搏鱼状态正常。
