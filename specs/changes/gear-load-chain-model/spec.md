# 承力件断件链与渔轮泄力模型

Status: done

## Problem Statement

玩家在搏鱼时，钓组会错误地只比较竿、主线和子线，铅芯前导、连接件和钩没有进入承力链；同强度或更弱的这些部件无法按其真实拉力断裂。渔轮又把当前泄力档位当成最弱承力件，导致低档位频繁被判“渔轮损坏”，但背包里的轮子耐久并未归零，出现提示损坏与物品状态不一致，鱼也无法正常通过泄力打滑逃窜。

## Solution

客户端通过 `17/9` 明确上报断件后，服务端只校验上报件的归属和装配关系，然后按上报件走对应断件通道：主线/前导/子线/铅芯/连接件 → 断线并计算下游丢失；钩/拟饵/饵/漂 → 摘除终端件；竿 → 断竿；渔轮 → 本体耐久直接归 0（官方表现），轮子留在竿上但不可用；主线、前导、拟饵等其余钓组组件退回背包。只有空/zero GUID、上报件缺失或出厂内嵌件时才回退到最弱环裁决；已存在但不受支持的装配品类判定为无效上报。摩擦档位不再否决或改判客户端上报的断件；线上 29（UI 30）锁轮时锁轮承力才参与回退候选。泄力打滑是独立事件，不再从 `17/9` 推断；摩擦片磨损仍保留在独立路径。断子线、连接件或铅芯时只删除该位置以下的终端件，不误删主线上游组件。断钩时挂在钩上的饵一并离组；断竿/断轮清空钓组后同时删除该竿的补饵请求和饵-钩映射；从背包堆拆出的子饵离组时并回来源堆，不在背包里留下独立一堆。

## User Stories

1. 作为玩家，我希望客户端上报哪一件断裂，服务端就损坏哪一件；服务端只做归属/装配校验，不按自己的最弱环改判。
2. 作为玩家，我希望客户端明确上报断线/断竿时，服务端一定产生真实断件，不会因为当前摩擦档位低于最弱件拉力就判成“泄力打滑”并保留整组钓具。
3. 作为玩家，我希望摩擦片磨穿后泄力归零、需要换片，但轮子本体和已装配状态仍保留。
4. 边界：客户端上报件与物理最弱环不一致时，按上报件处置；只有空/zero GUID、上报件缺失或出厂内嵌件才回退到最弱环裁决；已存在但不受支持的装配品类判定为无效上报。空 GUID / zero GUID 表示客户端未识别具体断件，走同一回退路径，不能无条件判成断竿。
5. 边界：旧存档里的摩擦片字段缺失时按额定值初始化；已持久化的 `0` 必须继续表示磨穿，不能重新满血。

## Implementation Decisions

- `internal/gameserver/gear_physics.go`：装配快照纳入竿、主线、前导/子线、铅芯前导、连接件、钩与锁轮承力；同强度时优先断下游便宜件。
- `internal/gameserver/gear_damage.go`：`17/9` 先校验上报件属于当前钓组，然后按上报件调用对应断件通道；空/zero GUID、上报件缺失或出厂内嵌件才回退最弱环；不受支持的装配品类拒绝上报；`17/9` 永远产生真实损坏，低档位不再从它推断泄力打滑；只有线上 29（UI 30）锁轮时锁轮承力加入回退候选；下游丢失集合按 `rigSlotTemplates` 中的断件位置计算。上报渔轮断件或回退判渔轮时，`damageReelLockOverload` 直接把本体耐久归 0（官方表现），不再按 20% 档逐次磨穿；同时把主线、前导、拟饵等其余钓组组件摘回背包，只在竿上保留损坏的渔轮；摩擦片磨损保留独立入口 `damageReelSlip`，不再由 `17/9` 触发。断钩时按 `bait_hook:<饵GUID>`（单钩钓组按钩位推断）把饵一并摘回；断竿/断轮删除该竿 `rebait:%` 与 `bait_hook:%`；拆分子饵通过事务内退款并回来源堆，并把来源堆加入 `StackRefreshGUIDs` 触发 4/22 刷新。
- `internal/gameserver/gear_physics.go`：`17/14` 摩擦档位是 0 基（客户端 UI = 线上值 + 1）；线上 0~28 对应 UI 1~29 的泄力刻度，线上 29 对应 UI 30 锁轮。线上 0 是有效的最小档，不能按“未设置”回退锁轮；没有 `17/14` 记录时按线上 15（UI 16）兜底，客户端一旦上报即落盘覆盖。
- `internal/gameserver/reel_performance.go`、`items.go`、`item_repair.go`、`reel_repair.go`：摩擦片制动力 `csDragForce` 作为持久化磨损状态，物品树下发、启动修复和零件重建都不得覆盖已存在的值。
- 数据与迁移：不新增表结构；使用既有 KV 标记执行一次性存量零值迁移，迁移可重复运行且只在标记缺失时执行。
- 兼容：客户端基线保持 `4.0.25034`；旧轮缺少摩擦片字段时补额定值，已有 `0` 保持磨穿；回滚方式为 revert 本 PR 的功能提交。

## Testing Decisions

- 存储与行为测试使用真实 SQLite 和仓库静态道具定义，覆盖摩擦片单次磨损、磨穿后再次打滑、`ItemToTree`、启动修复、零件重建和一次性迁移。
- 协议与装配测试覆盖真实装配铅芯前导的 `17/9` 上报、强钩弱线反向裁决，以及子线/连接件/铅芯断裂的下游丢失集合。
- 期望值来自道具定义的额定拉力、手算磨损步进和真实装配槽位关系，不用同一实现反算结果。
- 回滚后摩擦片复活、物品树回满、铅芯上报被拒、强钩弱线误判和上游铅芯误删等测试会重新变红。

## Out of Scope

- 不调整鱼种分布、咬钩概率、抛投距离公式或经济价格。
- 不新增客户端协议字段，不改数据库表结构。
- 不追求复刻官方未公开的全部耐久数值，只保证当前装配数据上的行为自洽。

## Further Notes

- `[事实]` 客户端会通过 `17/9` 上报钓组超载及断件；服务端必须再校验装配归属和实际最弱环，但“是否发生断裂”以上报为准，摩擦档位不能把它改成无损坏。
- `[事实]` `17/14` 摩擦档位抓包值是 0 基：客户端 UI 1 上报 0，UI 30 上报 29；实机日志 `值=29` 对应界面 30 锁轮。
- `[事实]` 摩擦片、导环等零件是装配件，本体损坏位与摩擦片磨损是不同状态。
- `[推断]` 现有真实道具的拉力字段足以支撑逐件最弱环判定；缺字段时仍保留兼容回退。
