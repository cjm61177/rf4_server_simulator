# 房屋仓库容器链路

Status: done

## Problem Statement

玩家在房屋中存放物品时，界面没有反应：已存入的物品不从背包消失，也不出现在房屋仓库。客户端已经发起 `4/1`、`4/4`、`4/5` 查询，服务端也完成了部分 `4/6` 落库，但房屋容器缺少数据映射、容量和树内容器枚举，导致客户端无法把物品挂进房屋容器。

## Solution

容器枚举 `10/11` 统一映射到玩家库的 `item.container='house'`。房屋仓库默认容量 100；`4/6` 在事务内校验容量并更新归属，成功后向本人推送 `4/21`（移除旧树）和 `4/22`（加入新树）。房屋物品的树内容器枚举固定投影为 10，背包/装备等既有路径保持不变。

## User Stories

1. 作为玩家，我希望打开房屋仓库时能看到已存物品，并能把背包物品即时存入房屋。
2. 作为玩家，我希望把物品从房屋取回背包时，背包和房屋界面同步更新。
3. 边界：房屋已满时，整次移动应失败且不移动任何物品，不能出现第 101 件或部分写入。
4. 边界：重复请求或同一 GUID 重复出现在请求中时，不应重复计数或产生错误的容量判断。

## Implementation Decisions

- `internal/gameserver/native_inventory.go`：补齐客户端容器枚举 `10/11` 到 `house` 的映射，供 `4/1`、`4/4`、`4/5` 共用。
- `internal/gameserver/handlers_game.go`：房屋容量常量 `houseContainerCapacity=100`，`4/1` 使用该常量回报普通容量。
- `internal/gameserver/items.go`：`canonicalizeItemPhysicalFields` 对 `container='house'` 的根物品投影 `mfllbndghhe=10`，其他根物品既有投影不变。
- `internal/gameserver/world.go`：`4/6` 使用短事务读取物品归属、校验房屋容量、批量更新后再提交；提交成功后推送 `4/21 + 4/22`。请求内 GUID 去重。
- 数据与迁移：不改变表结构；使用既有 `item.container` 和玩家库事务。容量按 100 起步，导入容量仍沿用既有 `importedContainerCapacity` 逻辑。
- 兼容：客户端基线 `4.0.25034`，复用已有 `24/27`、`4/21`、`4/22` 协议形状；回滚方式为 revert 本次改动，不改旧迁移。
- 回执：`4/6` 为幂等容器赋值，不产生额外经济收益；事务失败时回失败响应，不返回伪成功的 800 快照。

## Testing Decisions

- 存储/行为层使用真实 SQLite：覆盖 `4/1` 房屋计数与容量、`4/4` GUID 列表、`4/5` 物品树和树枚举 10/0。
- 行为层使用 tunnel probe：真实消费 `4/21` 和 `4/22`，断言顺序、GUID、目标容器枚举；覆盖背包→房屋、房屋→背包。
- 容量边界：创建 100 件房屋物品后尝试一次移动 2 件，断言失败且两件仍在背包、房屋数量不变。
- 去重边界：99 件房屋物品加同一件背包物品在请求中出现两次，仍应成功移动到 100 件。
- 导入容量：
ative-import 将容器 10 容量压到 2 时，4/1 展示 2，4/6 第 3 件必须被拒绝。
- 回滚后哪些测试会变红：移除 `10/11` 映射、容量校验、事务或 `4/21/4/22` 推送后，对应测试应失败。
- 测试不得使用 `t.Skip` 掩盖物品创建失败。

## Out of Scope

- 不改变背包、装备、帐篷、车辆、船只、滑板车和鱼护的容量规则。
- 不新增房屋升级/会员容量体系。
- 不改变 `4/6` 请求字段形状或客户端版本基线。

## Further Notes

`[事实]` 客户端打开房屋仓库会发起 `4/1(10)+4/4(10)+4/5`；修复前 `4/4` 和 `4/5` 可以返回数据，但树内 `mfllbndghhe` 始终为 0，客户端 UI 仍为空。

`[事实]` 修复前多次 `4/6` 已成功写入 `item.container='house'`，但客户端没有增量物品树更新，表现为存放无反馈。

`[事实]` 仓库容量约束要求写入操作原子化；本实现用玩家库事务保证多件移动全成或全败。
