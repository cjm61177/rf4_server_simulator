# 卡片入册与取回

Status: done

## Problem Statement

已钓到的卡片可以保存，但卡册操作只返回通用快照，没有保存收藏，玩家无法完成收集。

## Solution

为卡片入册和取回保存真实状态；卡册、背包与个人资料使用同一份收藏。操作失败整体回滚，重放不重复移动卡片。

## User Stories

1. 玩家将已拥有的卡片放进适用卡册，没有卡册时自动创建对应卡册。
2. 从卡册取回原卡，原鱼 GUID、重量、档位和钓获资料不变。
3. 重新登录后收藏保留，不额外抽卡或发奖励。

## Implementation Decisions

- 在 gameserver 注册 27/2、27/3，替代原先无副作用的世界快照处理器。
- [事实] command_contract.by_key 将 27/2 映射至 alpciclpmnn，签名为 string、Guid、Guid；27/3 映射至 hlmjcnikdpl，签名为 Guid。两者返回 pcnefbpgdhl/800。
- [事实] 27/2 原生入册操作的三个参数依次为卡册定义、卡册 GUID、卡片 GUID；新建卡册时第二项为空 GUID。27/3 使用卡片 GUID，原生取回按钮已由玩家实测通过。
- 沿用 dlbahppbdad/800：f0 空 args(61)、f1 args(61) 同步卡册及原卡、f2 空 GuidArr。入册只修改原卡父 GUID，不能将其作为删除项；取回清空父 GUID。卡册 f0 及个人资料 f9 使用362/364实例数组，详见 `trading-card-array-types`。
- [事实] 当前客户端入册成功回调会应用800；卡册视图从 StorageType 18 库存中筛选类别78、父GUID等于卡册GUID的卡片，无法仅靠卡册f0快照填充。4/1、4/4、4/5因此同时读取散卡、卡册及card_deck卡片，重新登录仍能还原卡位。
- 卡片原行保留，入册时移至 card_deck 容器，rig_guid 保存父卡册；卡册 f0 为同一事务内更新的投影。取回恢复原行；删除卡册沿用孤立附件退回背包机制。
- 不改表、不写静态库；校验卡册 cjmjfnheidh 定义、重复鱼种和物品归属。回执与移动在同一 SQLite 事务内写入 kv，键含玩家、token 哈希、命令、call_id，保存请求指纹和响应，防止崩溃重试撤销之后的操作。
- 已入册的掉落卡不因原鱼结算重放而再次作为背包项推送。
- 客户端基线 4.0.25034；实机验收与协议、临时库测试分别记录。玩家已确认收藏卡位、原生入册与取回按钮、重新登录均正常；其他玩家查看个人资料未单独验收。

## Testing Decisions

- 临时 SQLite：入册、重启读取、取回原卡；不适用卡册、重复鱼种、跨玩家和不属于背包的卡片不修改数据。
- 构造 27/2、27/3 请求经过注册分发与协议编解码，检查800同步原卡父GUID、无删除项、362/364实例数组及原鱼资料。
- 连续将两种卡片放入同一册，重建服务后通过4/1、4/4、4/5读取完整收藏库存，检查两张卡片均保留父GUID；取回后只改变原卡归属，不减少总数。
- 同一请求在后续取回后重放不能再次入册；人为让回执写入失败，确认卡册和卡片一起回滚。
- 完整 Go test/vet/build；不启动客户端，不向真实存档加测试物品。

验证：已核对原生27/2参数、800成功回调及卡册父GUID筛选流程。移动同步、两种卡片连续入册、服务重建后的完整库存读取、原卡取回、回执重放与事务回滚测试通过，完整Go test/vet/build通过。2026-11-07 玩家在修正版上完成“查看已有卡位 → 取回一张 → 再次入册 → 重新登录”，确认全部正常。多人并发操作与其他玩家查看个人资料未作完整实机验证。

## Out of Scope

卡片补录、覆膜、卡册兑奖、交易、资格任务。
