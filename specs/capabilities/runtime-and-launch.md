# 启动与进程装配 / 高频陷阱清单

> 用法：改 `cmd/*` 装配、初始化步骤、进程监管、端口与配置文件时对照本页。
> 部署操作步骤见 `docs/deploy.md`；静态库只读模型见 `docs/static_runtime_isolation.md`；
> 迁移与幂等见 `store-and-idempotency.md`。

## 1. 进程装配只有一个入口

- ✅ 每个进程的装配都在自己的 `cmd/<name>/main.go`：`gateway`（HTTPS 登录 + TCP realtime +
  隧道客户端）、`gameserver`（会话核 + 存储）、`seed`（初始化命令行）。
  - ❌ 在 launcher 里另写一套等价的装配逻辑 → 命令行与面板行为分叉，出问题只能猜走的是哪条。

## 2. 初始化步骤固定为四步且可重复执行

- ✅ `seed` 顺序固定：迁移 → 静态配置导入（幂等）→ 默认档案 → 默认管理员；
  launcher 内置同一套逻辑，不另立分支。
  - ❌ 把静态导入写成"一次性插入" → 二次启动直接失败，或数据被重复写入。
  - ❌ 跳过迁移直接建表 → 旧库升级路径没人走过。

## 3. 静态库始终只读

- ✅ 运行期用 `store.OpenWithStatic`：每条物理连接都挂 ATTACH 并对静态库加写保护；
  导入流程复用同一套 SQL 语义（`static_runtime_test` 专门盯这条等价性）。
  - ❌ 直接 `os.Open` 或独立连接写静态目录 → 下次发布被覆盖，或写保护失败导致连接报错。

## 4. 端口与地址来自配置

- ✅ 登录、realtime、隧道、管理端地址全部从 `config.yaml` 读，代码里不写死。
  - ❌ 在代码里兜底一个默认端口 → 换端口时只改了一半，进程起在错误地址上。

## 5. 启动期不假设别的进程已就绪

- ✅ 进程之间靠隧道/健康检查确认，launcher 负责重启与日志面板。
  - ❌ 用 `sleep` 或无限重试掩盖启动顺序问题 → 本机偶发失败，日志里看不出依赖关系。

## 提交前快速自检

- [ ] 装配改动落在对应 `cmd/<name>/main.go`，没有在 launcher 复制一份
- [ ] 初始化四步仍可重复执行
- [ ] 没有绕过 `OpenWithStatic` 直接写静态库
- [ ] 新增端口/地址全部走配置文件
